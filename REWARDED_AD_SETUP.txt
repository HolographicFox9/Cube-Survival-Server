HOSTL REWARDED AD SETUP

Game 642 no longer grants rewarded themes or the daily Wooden Chest from a plain browser request.
A reward requires a short-lived, replay-protected proof signed by a trusted backend after the ad
provider confirms completion.

1. SET A PRIVATE SERVER SECRET
Set an environment variable on the HOSTL server:
  HOSTL_REWARDED_AD_SECRET=<random secret of at least 32 characters>

Never place this secret in public/index.html, localStorage, browser JavaScript, or an ad callback that
runs only in the player's browser.

2. ISSUE A COMPLETION PROOF FROM TRUSTED SERVER CODE
After the ad network/provider verifies a completed rewarded ad, create a JSON payload:
  {
    "uid": "HOSTL account userId",
    "kind": "theme" | "dailyChest",
    "subject": "themeId or UTC YYYY-MM-DD",
    "iat": 1234567890000,
    "exp": 1234567890000,
    "jti": "unique one-time id"
  }

Use millisecond timestamps. exp must be no more than 30 minutes after iat.

Encode/sign it as:
  body = base64url(UTF8(JSON.stringify(payload)))
  sig  = base64url(HMAC-SHA256(HOSTL_REWARDED_AD_SECRET, body))
  proof = body + "." + sig

Each jti must be unique. HOSTL remembers consumed proof IDs and rejects replayed rewards.

3. CONNECT THE BROWSER AD PROVIDER
The game looks for this integration hook:
  window.__hostlRewardedAdProvider(kind, subject)

That function should:
- show the rewarded ad,
- wait for the provider's successful completion confirmation,
- ask your trusted backend for the signed proof,
- return that proof string to HOSTL.

For theme unlocks:
  kind = "theme"
  subject = the requested theme ID

For the daily Wooden Chest:
  kind = "dailyChest"
  subject = the current UTC date in YYYY-MM-DD form

If the server secret/provider is not configured, HOSTL deliberately leaves rewarded-ad rewards locked.
This is safer than the old test hook, which granted rewards without proving an ad was watched.
